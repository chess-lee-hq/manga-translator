## 2단계 — 안정성·비용·입력 개선

| # | 문제 | 수정 | 주요 파일 |
|---|---|---|---|

| 2 | **(테스트 중 발견, 기존 버그)** 3장을 동시에 번역하면 ONNX 세션 동시 실행 오류(`Session already started`)로 2장이 실패 | 말풍선 검출 추론을 큐로 직렬화. 모델 로드 실패 후 재시도 가능 | `src/lib/yolo.ts` |

| 4 | API 키를 한 글자씩 치면 첫 글자에서 번역 시작 → 실패로 남음 | 키 입력이 800ms 멈춘 뒤에만 번역 시작. 저장된 키는 첫 렌더부터 읽어 지연 없음 | `src/App.tsx` |
| 5 | 실패 원인이 콘솔에만 찍히고 화면엔 "오류 발생"만. 키가 없어도 "번역 실패"로 표시 | 페이지별 오류 메시지 + 페이지별 다시 시도. 키 없음/자동 번역 꺼짐/대기/번역 중 상태 구분. 덮어쓰기 모드용 하단 바 상태 표시. 같은 키로 실패한 페이지는 자동 재호출 안 함(키를 바꾸면 재시도) | `src/App.tsx` |

| 7 | 백업을 불러오면 단어장을 덮어씀(옛 백업이면 삭제) | 현재 단어장에 병합, 병합 개수 안내 | `src/App.tsx` |

### 사용자가 느끼는 변화
- 새로고침하거나 탭을 닫았다 열어도 마지막 작품·페이지로 돌아옴. 새 작품은 **작업 닫기** 후 시작
- 페이지 이탈 경고는 저장이 끝나지 않았거나 ZIP 내보내기 중일 때만 표시 (IndexedDB를 못 쓰는 환경에선 예전처럼 항상 경고)
- 번역 중에도 화면이 끊기지 않음
- 첫 로딩 JS 1.12MB → 722KB (검출 코드 407KB는 번역이 시작될 때 Worker로 따로 로드)

### 새 브라우저 저장소
- IndexedDB `manga-translator` (`pages`, `meta`). 이전 단계로 되돌리면 사용되지 않고 남을 뿐 문제없음
- 지우려면 브라우저 콘솔에서 `indexedDB.deleteDatabase('manga-translator')`

## 추가 수정 4 — 놓친 글자·중복 번역·맥락 기억 (1·2단계)

### 1단계 — 검출과 중복 (API 비용 증가 없음)

| 문제 | 수정 | 파일 |
|---|---|---|
| 검은 배경의 흰 글씨를 검출하지 못해 번역에서 빠짐 | 어두운 픽셀이 5% 이상인 페이지는 색을 뒤집어 한 번 더 검출하고 결과를 합침 (모델이 학습한 "밝은 배경의 검은 글씨" 형태가 됨). 해당 페이지만 검출 시간 2배 | `lib/yolo.worker.ts`, `lib/yoloPostprocess.ts` |
| 같은 대사가 두 번 번역됨 | ① 큰 박스 안에 70% 이상 들어간 작은 박스는 버림 (IoU 기준만으로는 안 걸러짐) ② 모델이 같은 칸 번호를 두 번 돌려주면 첫 응답만 사용 | `lib/yoloPostprocess.ts`, `lib/translatePage.ts` |
| 박스를 딱 맞게 잘라 글자 획이 잘림 | 크롭에 사방 8% 여백 + 고품질 보간 | `lib/imageUtils.ts` |
| 작은 말풍선에서 글자가 넘침 | 최소 글자 크기 13px → **10px** (배율 100% 기준, 화면·저장 공통) | `lib/overlayLayout.ts` |

### 2단계 — 말투·맥락 기억

- **직전 대사 전달:** 이미 번역된 앞 페이지의 대사(최대 16줄)를 "이어지는 맥락"으로 프롬프트에 넣어 말투·호칭·고유명사를 일관되게 유지. 병렬 번역으로 바로 앞 페이지가 아직 없으면 번역이 끝난 가장 가까운 앞 페이지를 사용 (`lib/translationContext.ts`)
- **작품 노트:** 번역이 쌓이면(처음 3장, 이후 10장마다) Gemini가 인물별 말투·호칭·고유명사 표기를 요약해 저장하고, 이후 모든 번역 프롬프트에 함께 전달. 헤더 **[작품 노트]** 에서 직접 편집·AI 재정리 가능. 작품별로 저장되고 백업 ZIP에 포함 (`lib/workNotes.ts`, `hooks/useWorkNotes.ts`, `components/WorkNotesModal.tsx`)
- **문맥 우선 모드:** 작품 노트 창의 체크박스. 동시 3장 → 1장으로 낮춰 한 장씩 순서대로 번역해 앞 내용을 최대한 반영 (느리지만 일관성 최고)
- **버그 수정(테스트 중 발견):** 새로고침 직후 저장된 노트를 읽기 전에 자동 갱신이 먼저 돌아 불필요한 Gemini 요청 1회 + 오류 배너가 떴음 → 작품 노트를 같은 렌더에서 바로 읽도록 수정, 자동 갱신 실패는 배너 없이 로그만 남김

새 저장값: `manga-notes-<작품 이름>`, `manga-translator-auto-notes`, `manga-translator-context-first`. 이전 버전으로 되돌리면 무시될 뿐 문제없음

### 검증
- `tsc -b` 통과, `vitest` 75개 통과(중복 박스 정리·칸 중복 응답·맥락 수집 등 14개 추가), `vite build` 성공
- 브라우저(가짜 Gemini 응답, 3장):
  - 어두운 페이지(어두운 비율 0.665)에서 색 반전 재검출이 돌아 흰 글씨 1개 검출, 밝은 페이지는 재검출 없이 종료
  - 2번째 페이지 요청에 1번째 번역이, 3번째 요청에는 1·2번째 번역이 포함됨 (문맥 우선 모드)
  - 작품 노트 자동 생성·저장, 편집창 반영, AI 재정리 동작
  - 새로고침 후 불필요한 Gemini 요청 0회, 오류 배너 없음
  - 아주 작은 박스(폭 4.5% × 높이 1.5%)에서 글자 10px 적용
- **실제 만화로는 확인하지 못함.** 효과음 판별과 마찬가지로 반전 검출·중복 제거 기준값은 추정치이므로, 실사용에서 과·소 검출이 보이면 기준값 조정 필요

## 추가 수정 7 — Gemini 토큰 절감 · [임시] OpenAI 비전 단독 테스트 토글

### 왜
OpenAI 모드에서는 번역을 OpenAI가 하는데도 Gemini에게 **전체 페이지 이미지 + 격자 이미지 2장**을 보내고 **번역문까지** 받아 버리고 있었다(받은 번역문은 쓰지 않고 버림). 또한 OpenAI가 이미지를 직접 읽을 수 있으므로 Gemini 없이도 되는지 실제 품질로 비교해볼 필요가 있었다.

| 변경 | 내용 | 파일 |
|---|---|---|
| ① Gemini 토큰 절감 | OpenAI 모드에서는 Gemini에게 **격자 이미지 1장만** 보내고 **원문 읽기(OCR)만** 요청. 전체 페이지 이미지·단어장·맥락 지시문을 빼고, 응답 스키마에서도 `translated_text`를 제거해 출력 토큰도 줄임. Gemini 모드(제공자=Gemini)는 이전과 완전히 동일 | `lib/gemini.ts`, `lib/translatePage.ts` |

## 추가 수정 9 — 세로쓰기 과다 판정 수정 · 격자 배치 토큰 최적화

### 1) 세로쓰기가 너무 쉽게 걸리던 문제
원문이 세로 한 줄이라 아주 좁게 잡힌 박스는, 번역문이 짧아 가로로 몇 자만 넣으면 충분한데도 무조건 세로쓰기로 나오고 있었다.
원인: 세로/가로 판별이 **박스 원래 너비**만 보고 있었음. 하지만 가로쓰기는 실제로 흰 상자를 박스 너비의 최대 2배(`maxWidthRatio`)까지 넓혀서 쓸 수 있는데, 판별은 그 확장 가능성을 무시하고 있었다.

| | 전 | 후 |
|---|---|---|
| 판별 기준 | 박스 원래 너비 vs 최소 글자 크기 | **가로쓰기가 최대로 넓힐 수 있는 너비**(박스 너비 × 2) vs 최소 글자 크기 |
| 효과 | 원문이 세로 한 줄이면 번역문 길이와 무관하게 세로쓰기 | 짧은 번역문은 넓혀서 가로쓰기, 정말 좁은 박스만 세로쓰기 유지 |

파일: `lib/overlayLayout.ts` (`resolveTextDirection`)

### 2) 격자 이미지 배치를 토큰이 적게 드는 모양으로 자동 선택
전에는 말풍선이 몇 개든 항상 3열 고정이었다. 이제 칸 수에 맞춰 OpenAI 비전(고해상도) 토큰 추정치가 가장 적은 열 수를 계산해서 고른다.

- 새 파일 `lib/gridLayout.ts`: `estimateVisionTokens(width, height)` — 문서화된 계산식(장변 2048 → 단변 768 → 512px 타일) 기반 추정치. gpt-5.6 계열의 정확한 값은 공개되어 있지 않아 **추정치**이며 실제 청구 토큰과 다를 수 있음
- `chooseGridColumns(cellCount, cellSize)` — 토큰 최소 → 정사각형에 가까운 쪽 → 낭비 칸 적은 쪽 순으로 열 수 선택
- 칸 하나의 실제 크기(300×300)는 그대로라 글자 인식 품질에는 영향 없음 (배치만 바뀜)
- 예: 칸 6개는 2×3(전 3×2와 토큰 동일), 칸 9개는 3×3(정확히 채움), 칸 11개는 3×4

파일: `lib/gridLayout.ts`(신규), `lib/imageUtils.ts` (`createGridImageFromBoxes`가 `gridWidth` 생략 시 자동 계산)

## 추가 수정 11 — 첫 로딩 용량 절반 (WASM CPU 전용 · 모델 fp16 가중치 · 템플릿 잔재 정리)

사용자가 처음 앱을 열 때 받는 파일은 **말풍선 검출 모델 + onnxruntime WASM**이 대부분이다. 둘 다 검출 결과를 바꾸지 않는 방법으로 줄였다.

### 1) onnxruntime을 CPU 전용 빌드로 (커밋 `4fe7276`)
| | 전 | 후 |
|---|---|---|
| import | `onnxruntime-web` (WebGPU 포함판) | `onnxruntime-web/wasm` (CPU 전용 — 실제로 CPU만 씀) |
| WASM | 26.5MB (압축 전송 약 6.7MB) | **13.3MB** (압축 전송 약 3.7MB) |
| 워커 JS | 0.39MB | 0.07MB |
| CDN 주소 버전 | `1.29.0` 하드코딩 | 설치된 패키지 버전에서 자동 (`ort.env.versions.web`) → 패키지만 올리고 주소를 깜빡해 JS·WASM이 어긋나는 위험 제거 |

배포 빌드 A/B(같은 조건 반복): 검출 좌표·신뢰도 **완전히 동일**, 워밍 후 추론 약 740ms 동일, 캐시된 첫 검출 약 2.4초 → 2.1초.

### 2) 검출 모델 가중치를 float16으로 저장 (43MB → 21.5MB)
Conv 가중치·편향 127개를 float16으로 저장하고, 그래프 앞의 Cast 노드가 실행 시 float32로 되돌린다. 계산 경로는 원본과 같다.

시험한 방식 (합성 페이지 24장 기준, 원본 fp32와 비교):
| 방식 | 크기 | 결과 | 판정 |
|---|---|---|---|
| 동적 양자화 uint8 | 11.0MB | 박스 일치 70%, 더 느림(501ms) | ✗ |
| int8 가중치(전체) | 10.9MB | 빠진 박스 0, **추가 박스 6개**, 점수 차 최대 0.70 | ✗ |
| int8 + 검출 헤드 원본 유지 | 17.0MB | 추가 박스 6개(신뢰도 0.26~0.32) 그대로 | ✗ |
| **fp16 가중치** | **21.5MB** | 추가 0 · 빠진 0, 점수 차 최대 0.03, 속도 동일 | **✓ 채택** |

브라우저(WASM) 확인: 16장 74박스 중 72개 일치, 추가 박스 0, 속도 동일(733 vs 746ms). 짝을 못 찾은 2개는 원본 신뢰도가 **0.251**(기준 0.25에서 0.001 차)이던 경계선 박스로, fp16에서 0.249가 되어 기준 아래로 내려간 것.

- 파일 이름을 `manga109_yolo_s_fp16w.onnx`로 바꿔 사용자 브라우저에 남은 옛 모델 캐시와 섞이지 않게 함
- 변환 스크립트 `scripts/convert_yolo_fp16_weights.py` 추가 (산출물이 배포 모델과 바이트 단위 동일함을 확인)
- 원본 fp32 모델은 저장소에서 삭제 (복구: `git show 4fe7276:public/manga109_yolo_s.onnx > public/manga109_yolo_s.onnx` 후 `yolo.ts` 파일명 되돌리기)

### 3) 템플릿 잔재 정리
`src/App.css`, `src/assets/{hero.png,react.svg,vite.svg}`, `public/icons.svg`(참조 없음), `test-lint.json`(실제 설정은 `.oxlintrc.json`) 삭제. `index.html`의 `lang="en"` → `lang="ko"`.

|---|---|---|
| 배포 폴더(dist) | 71MB | **36MB** |
| 첫 방문 시 받는 모델+WASM (압축 전) | 43 + 26.5 = 69.5MB | 21.5 + 13.3 = **34.8MB** |

### 검증

## 추가 수정 12 — 자동 품질 검사 + 실패한 칸만 재요청

번역 결과에서 **기계적으로 판정되는 실패**만 골라, 그 칸만 작은 격자로 다시 만들어 **한 번 더** 요청한다. ("어색한 번역" 같은 주관적 판단은 하지 않음)

### 판정 규칙 (`lib/translationQuality.ts`)
| 문제 | 조건 | 처리 |
|---|---|---|
| 응답 누락 | 모델이 그 칸 번호를 아예 돌려주지 않음 | 재요청 |
| 빈 번역 | 원문에 글자가 있는데 번역문이 비어 있음 | 재요청 |
| 미번역 | 번역문에 한글이 하나도 없고 일본어(가나·한자)만 있음 (원문 베끼기) | 재요청 |
| 일본어 남음 | 번역문에 가나가 2자 이상, 한글 대비 20% 이상 섞임 (예: "그건 さくら의 거야") | 재요청 |
| 태그 누출 | 번역문 앞에 `[대사]`·`【효과음】` 등 | **재요청 없이** 바로 제거 |
| 글자 없는 칸 | 원문·번역 모두 비어 있음 (그림을 글자로 잘못 잡은 자리) | 재요청 안 함 → 기존대로 자동 삭제 |

- 장음 부호 `ー`·가운뎃점 `・`·문장부호·숫자는 일본어로 치지 않음 (예: "으아ー!", "100엔"은 통과)
- 재요청 결과는 문제 심각도(누락 > 빈 번역 > 미번역 > 일본어 남음 > 정상)를 비교해 **더 나은 쪽만** 채택. 같거나 더 나쁘면 원래 결과 유지
- 재요청은 **1회만**. 재요청이 실패(429 등)해도 첫 결과로 계속 진행하고 페이지를 실패 처리하지 않음
- 재요청 프롬프트에는 "앞선 응답에서 비었거나 일본어가 남았다, 반드시 한국어로" 안내를 덧붙임 (`RETRY_INSTRUCTION`)

### 적용 범위
한 장 번역, 3장 묶음 번역, 직접 그린 영역 번역 모두 같은 헬퍼(`translateGridWithQualityCheck`)를 거친다. 묶음에서는 여러 페이지에 걸친 문제 칸을 한 격자로 모아 재요청하고, 결과를 원래 페이지·칸으로 되돌린다. OpenAI·Gemini 둘 다 적용. (말풍선을 못 찾아 페이지 전체를 읽는 대체 경로는 칸 구조가 없어 태그 제거만 적용)

### 확인 방법
- 콘솔 `[quality] 4칸 중 3칸 문제(빈 번역 1, 미번역 1, 응답 누락 1) → 재요청 후 3칸 해결`
- 토큰 로그에 `격자 재요청 (품질 검사)` 항목으로 재요청 비용이 따로 찍힘

### 기타
- 격자 번역 호출을 `gridRequesterFor(settings)` 하나로 모아 세 경로의 중복 제거
- `translateGridImageOpenAI`의 7번째 인자를 옵션 객체(`{ pageCellCounts, label }`)로, Gemini 격자 옵션에 `label` 추가
- 안 쓰게 된 `createGridImageFromBoxes` 삭제

### 검증
- `tsc -b` 통과, `vitest` **128개** 통과(품질 검사 15건 추가), `oxlint` 경고 12개(동일), `vite build` 통과
- 브라우저(가짜 API가 일부러 빈 번역·일본어 그대로·칸 누락·`[대사]` 태그를 섞어 응답): 4장 올림 →
  - 보이는 1·2장: 각각 4칸 중 3칸 문제 → 3칸만 재요청 → 3칸 모두 복구, 태그 제거됨
  - 3·4장 묶음(7칸): 두 페이지에 걸친 문제 3칸만 모아 재요청 → 3장 2칸·4장 마지막 칸으로 정확히 되돌아감
  - 요청 수: 첫 요청 3회 + 재요청 3회. 재요청 격자는 문제 칸 수(3칸)만큼만 전송

## 추가 수정 15 — 화자 힌트 (YOLO 얼굴·몸 검출 활용)

YOLO는 원래 몸(0)·얼굴(1)·컷(2)·말풍선(3)을 모두 검출하지만 지금까지 얼굴·몸은 버리고 있었다. 이제 말풍선마다 가장 가까운 인물을 짝지어 **"같은 컷에서 어느 말풍선끼리 같은 인물인지"**를 번역 프롬프트에 알려준다. 대화의 주고받음을 알면 반말/존댓말이 페이지 안에서 뒤집히는 실수가 줄어든다. 추가 요청·계산 비용은 거의 없음(프롬프트 몇 줄).

### 추정 규칙 (`lib/speakerHints.ts`)
| 규칙 | 값 |
|---|---|
| 짝짓기 | 말풍선 중심에서 **같은 컷 안의** 가장 가까운 얼굴. 얼굴이 없으면 몸(위 15% 머리 쪽) |
| 너무 멀면 | 페이지 대각선의 25%보다 멀면 모름 |
| 애매하면 | 1등과 2등 인물 거리 차가 대각선의 3% 미만이면 판단하지 않음 |
| 다른 컷 | 서로 다른 컷의 얼굴이 같은 인물인지는 알 수 없으므로, "다른 인물" 판단은 **같은 컷 안에서만** |
| 컷을 못 찾은 경우 | 같은 얼굴에 붙은 말풍선끼리 "같은 인물"만 알림 |

프롬프트 예:
```
# 화자 힌트 (말풍선과 가장 가까운 얼굴 위치로 추정한 것이라 틀릴 수 있음 — 말투·존댓말을 정할 때 참고만 해)
- 같은 컷: #1 / #2·#3 (묶음마다 다른 인물)
```

### 적용 범위
한 장 번역·3장 묶음 번역(페이지끼리 섞이지 않게 화자 키에 페이지 ID 포함)·품질 검사 재요청(문제 칸의 화자 정보 유지). OpenAI·Gemini 모두. 알려줄 정보가 없으면(인물 미검출, 한 컷에 말풍선 하나) 프롬프트에 아무것도 넣지 않음. 콘솔 `[speaker] 말풍선 4개 중 3개 화자 추정 (얼굴 3 · 몸 0)`.

### 검증
- `tsc -b` 통과, `vitest` **153개** 통과(화자 추정 10건 추가), `oxlint` 경고 12개(동일), `vite build` 통과
- 브라우저: 직접 그린 단순한 얼굴은 YOLO가 얼굴로 인식하지 않음(실제 만화 인물로 학습된 모델) → YOLO가 실제로 찾은 컷 2개·말풍선 4개에 그림 속 얼굴 위치 3개를 더해 확인. 위 컷의 오른쪽 인물 옆 말풍선(#1)과 왼쪽 인물 옆 두 말풍선(#2·#3)이 서로 다른 인물로 묶이고, 아래 컷의 단독 말풍선(#4)은 힌트 없음. OpenAI 요청 프롬프트에 `# 화자 힌트` 포함 확인
- 한계: 실제 만화에서 얼굴 검출 비율·짝짓기 정확도는 실사용으로 확인 필요

## 추가 수정 16 — 영역 수정 UI 정리 3건

### 1) 세로쓰기일 때 묶음/풀림 숨김
`disable_keep_all`은 **가로쓰기**의 음절 단위 줄바꿈만 바꾸는데, 세로쓰기(`layoutVerticalText`)는 항상 한 글자씩 쌓아서 이 값을 아예 쓰지 않는다. 그런데도 버튼은 세로쓰기일 때도 그대로 떠 있어 "가로/세로랑 뭐가 다른 거지" 싶게 만들었다. 이제 세로쓰기에서는 묶음/풀림 버튼 자체를 숨긴다. (`BoxEditor`에 `textDirection !== 'vertical'`일 때만 렌더링)

### 2) 작게(딱지) 위치를 직접 드래그로 지정
`layoutTags`(오른쪽→왼쪽→아래→위→네 모서리 자동 배치)만 있던 것에, 딱지를 박스처럼 **드래그로 옮기는** 기능을 추가했다.

| 항목 | 내용 |
|---|---|
| 저장 필드 | `tag_pos?: [number, number]` — 딱지 좌상단 위치, `box_2d`와 같은 0~1000 정규화 좌표 |
| 동작 | `tag_pos`가 있으면 `layoutTags`가 자동 배치 후보 탐색을 건너뛰고 그 자리를 그대로 씀 (단, 페이지 밖으로 나가면 안쪽으로 당김) |
| 다른 딱지와의 관계 | 수동으로 고정한 딱지도 `placed` 목록에 들어가 **뒤이어 자동 배치되는 다른 딱지가 피해감** |
| 되돌리기 | 딱지에 마우스를 올리면 뜨는 되돌리기 버튼(↺) — 누르면 `tag_pos`를 지우고 자동 배치로 복귀 |
| 화면·저장 공유 | 화면(`MangaViewer`)과 이미지 내보내기(`exportCanvas`)가 같은 `layoutTags`를 그대로 쓰므로 드래그한 위치가 저장 이미지에도 동일하게 반영됨 |
| 크기 조절 없음 | 딱지 크기는 텍스트 길이로 자동 결정되므로, 이 드래그 박스는 이동 전용(`BoxEditor`에 `resizable={false}` 추가) |

### 3) 덮어쓰기 모드에서 바로 삭제
지금까지 번역 삭제는 오른쪽 대본 패널에만 있어서, 화면을 보다가 지우려면 패널로 눈을 옮겨야 했다. `BoxEditor`에 삭제 버튼(휴지통, 위쪽 가운데)을 추가해 덮기·작게 모드의 영역 수정 화면에서 바로 지울 수 있다. 기존 대본 패널의 확인창(`이 번역을 삭제하시겠습니까?`)과 같은 핸들러(`handleDeleteBubble`)를 그대로 씀.

### 새 저장 필드
`tag_pos?: [number, number]` — 없으면 이전과 동일하게 자동 배치. 이전 버전으로 되돌려도 이 필드는 무시될 뿐 문제없음.

### 검증
- `tsc -b` 통과, `vitest` **157개** 통과(`layoutTags` tag_pos 3건·검증 규칙 1건 추가), `oxlint` 경고 12개(동일), `vite build` 통과
- 브라우저: 세로쓰기 박스에 묶음/풀림 버튼이 없고 가로쓰기 박스에는 있음을 버튼 목록으로 확인. 딱지를 포인터 이벤트로 드래그 → `tag_pos` 저장 확인 → 새로고침 후에도 위치 유지 → 되돌리기 버튼으로 `tag_pos` 제거·자동 배치 복귀 확인. 덮어쓰기 모드에서 삭제 버튼으로 항목 하나를 지우고 나머지 2개는 그대로인 것 확인

## 추가 수정 17 — 딱지 크기 조절 · 영역 수정 툴바를 아이콘 한 줄로

### 1) 작은 딱지(효과음 등) 크기를 드래그로 조절
지난 패치에서 딱지 위치를 드래그로 옮기게 했는데, 크기는 텍스트 길이로 자동 결정되던 것을 이제 **우하단 손잡이로 직접 키우거나 줄일 수 있게** 했다.

| 항목 | 내용 |
|---|---|
| 저장 필드 | `tag_scale?: number` — 기본 크기의 배율(1이 기본), 허용 범위 0.5~3배(`TAG_SCALE_MIN`/`MAX`) |
| 동작 | 손잡이를 끌면 시작 크기 대비 커진(또는 작아진) 비율만큼 `tag_scale`에 곱해 반영. 폰트 크기·안쪽 여백·최대 줄 너비·모서리 둥글기·그림자가 모두 이 배율에 비례 |
| 위치와 구분 | 같은 박스를 몸통으로 끌면 이동(`tag_pos`), 모서리 손잡이로 끌면 크기(`tag_scale`) — 크기 변화가 2% 미만이면 이동으로만 처리해 손 떨림에 의한 오작동 방지 |
| 되돌리기 | 툴바의 되돌리기 버튼 하나로 위치·크기를 **한 번에** 자동 값으로 복귀 |
| 화면·저장 공유 | `layoutTags`가 돌려주는 `TagLayout.scale`을 화면(`MangaViewer`)과 이미지 내보내기(`exportCanvas`)가 그대로 써서 조절한 크기가 저장 이미지에도 동일하게 반영됨 |

### 2) 영역 수정 툴바를 아이콘 한 줄로 정리
말풍선마다 코너 4곳에 흩어져 있던 기능 배지(덮기/작게, 가로/세로, 묶음/풀림, 삭제)를 **박스 위 가운데 아이콘 한 줄**로 모았다. 작은 말풍선에서 배지끼리 겹치던 문제도 함께 줄었다.

| 버튼 | 아이콘 (상태별) |
|---|---|
| 표시 방식 | 덮기 = `Square`, 작게 = `Tag` |
| 글자 방향 | 가로 = `ArrowLeftRight`, 세로 = `ArrowUpDown` |
| 묶음/풀림 | 묶음 = `Link2`, 풀림 = `Unlink2` (세로쓰기에서는 여전히 숨김) |
| 위치·크기 되돌리기 | `Undo2` |
| 삭제 | `Trash2`, 구분선 뒤 빨간 강조 |

**말씀대로 우하단 크기 조절 손잡이(파란 원)는 그대로 뒀고**, 다른 기능만 툴바로 모았다.

### 검증
- `tsc -b` 통과, `vitest` **160개** 통과(`layoutTags` tag_scale 4건·`sanitizeResults` 검증 1건 추가), `oxlint` 경고 12개(동일), `vite build` 통과
- 브라우저: 딱지 손잡이를 자연스러운 지연을 두고 드래그 → `tag_scale: 2.89` 저장, 화면에서 글자가 눈에 띄게 커짐 확인. 되돌리기 버튼으로 `tag_pos`·`tag_scale` 동시 제거 확인. 새 툴바에서 가로쓰기(4개 버튼)·세로쓰기(3개, 묶음 없음)·딱지 원문 영역(3개, 방향 없음) 각각 올바른 버튼 구성 확인
- 디버깅 메모: 빠른 자동화 스크립트로 포인터 이벤트를 연속 발사하면 React가 내부 `ref` 이펙트를 미처 반영하기 전에 `pointerup`이 도착해 크기 변화가 0으로 읽히는 현상이 있었음 — 실제 사용자 드래그(이벤트 사이에 자연스러운 간격 존재)에는 해당하지 않는, 테스트 스크립트 자체의 타이밍 문제였음

### 2) 재요청: 2배 해상도 + 다른 엔진 (5-1, 5-4)
품질 검사(빈 번역·일본어 남음·응답 누락)에 걸린 칸만 다시 보내는 단계를 강화했다.

| 항목 | 내용 |
|---|---|
| 해상도 | 칸 한 변 300px → **600px**, JPEG 0.8 → **PNG** (작은 글씨·한자 획 뭉개짐 방지). 칸 번호 글자도 같은 비율로 키움 |

| 토큰 로그 이름 | `격자 재요청 (고해상도 · Gemini)` / `격자 재요청 (고해상도 · Sol)` |
| 비용 감각 | 재요청 1장(3칸) 이미지 약 1,445토큰 추정(OpenAI 타일 계산식 기준), 1칸이면 약 765토큰. 문제 칸이 없으면 추가 비용 0 |

주의: 원본 스캔 자체가 작으면 2배로 키워도 새 정보가 생기지는 않는다(획이 커져 읽기 쉬워지는 효과만 있음). 또 품질 검사는 **기계적으로 드러나는 실패만** 잡으므로, 그럴듯하게 잘못 읽은 글자는 여전히 이 경로를 타지 않는다.

## 추가 수정 21 — 원본 말풍선 모양에 맞춰 번역문 넣기 (1-A)

지금까지는 모든 대사를 글자 영역 기준의 **둥근 사각형**으로 덮었다. 이제 흰 말풍선이면 **원본 말풍선 모양 그대로** 원문을 지우고, 줄마다 그 높이의 말풍선 폭에 맞춰 번역문을 놓는다. 추가 모델·API 토큰은 없다(페이지 이미지 픽셀만 읽음).

### 1) 말풍선 모양 찾기 (`lib/bubbleShape.ts`)
글자 영역 안쪽의 흰 픽셀에서 시작해 흰색을 바깥으로 채워 나가면 말풍선 테두리에서 멈춘다. 채운 영역 + 그 안에 갇힌 글자 획 = 말풍선 안쪽 모양.

| 단계 | 내용 |
|---|---|
| 흰색 기준 | 글자 영역 밝기 상위 10%를 종이색으로 보고(누런 스캔 대응), 190보다 어두우면 흰 말풍선이 아님 |
| 격자로 줄이기 | 긴 변 최대 320칸, 칸 안의 **가장 어두운** 픽셀을 써서 가는 테두리가 끊기지 않게 함 |
| 시작점 | 글자 영역 안쪽 60%의 흰 칸 (검출 박스 모서리가 말풍선 밖에 걸쳐도 안전) |
| 구멍 채우기 | 바깥에서 닿지 않는 칸(글자 획, 口 같은 글자 속 구멍)을 모양에 포함 |

**확실하지 않으면 포기하고 둥근 사각형으로 되돌린다.**
- 흰색이 탐색 범위 끝까지 번짐 → 테두리가 끊긴 말풍선, 말풍선 없는 글자
- 말풍선 면적이 글자 영역의 12배 초과 → 그림의 흰 배경으로 번짐
- 배경이 흰색이 아님 → 스크린톤·그림 위 글자
- 원문 글자 획의 4% 넘게 모양 밖에 남음 → 글자가 테두리에 걸침
- 다른 글자 영역의 중심이 같은 모양에 들어옴 → 붙은 말풍선의 경계가 끊김

### 2) 모양 안에 번역문 배치 (`lib/bubbleLayout.ts`) — 글자가 너무 작아지지 않게 단계적으로 물러남

| 순서 | 방법 |
|---|---|
| ① | 줄마다 그 높이의 말풍선 폭으로 어절 단위 줄바꿈, 글자 덩어리는 말풍선 무게중심에 (꼬리가 있어도 몸통 가운데로) |
| ② | 줄 간격 1.15 → 1.02로 조여 다시 시도 |
| ③ | **최소 글자 크기 12px**(배율 100% 기준, 네모 상자의 10px보다 높게) 아래로는 줄이지 않음 |
| ④ | 그래도 넘치면 흰 영역을 말풍선 모양 그대로 1.08배 → 1.16배 키움 (면적 약 1.17 → 1.35배) |
| ⑤ | 그래도 넘치면 지금의 둥근 사각형 덮기 |
| 기타 | 두 글자도 못 들어가는 뾰족한 끝 줄은 쓰지 않음. 어절을 자르지 않는 배치를 ④까지 모두 찾아본 뒤에만 글자 단위로 자름 |

화면(`BubbleFitText`)과 이미지 저장(`exportCanvas`)이 같은 배치 결과를 그린다. 모양 찾기는 보이는 페이지만 화면 표시 뒤 비동기로 하고(페이지 40장까지 기억), 배치 결과는 모양·글·페이지 크기별로 재사용한다.

### 3) 영역 수정 모드
| 항목 | 내용 |
|---|---|
| 말풍선 맞춤 토글 (`MessageCircle`) | 모양을 찾은 항목에만 표시. 끄면 둥근 사각형, 켜면 박스를 고친 항목도 맞춤 (`fit_bubble` 저장, 백업·불러오기 검증 포함) |
| 자동 규칙 | 덮기 방식이고, 박스를 직접 옮기거나 크기를 바꾸지 않았고, 세로쓰기를 직접 고르지 않았을 때 맞춤 |
| 넘침 표시 | ④ 흰 영역을 키웠거나 ⑤ 둥근 사각형으로 넘어간 항목은 박스 왼쪽 위에 **주황 점** |
| 짧게 다시 번역 (`Scissors`) | 넘친 항목에만 표시. 12px로 들어가는 글자 수를 계산해 "공백 포함 N자 이내, 뜻·말투 유지"로 OpenAI에 요청 1회. 결과가 더 길면 바꾸지 않음. **자동으로 줄이지는 않음** |

### 검증
- `tsc -b` 통과, `vitest` **182개** 통과(말풍선 모양 6건: 닫힌 말풍선·말풍선 없는 글자·끊긴 테두리·스크린톤·붙은 말풍선·테두리에 걸친 글자 / 배치 6건: 줄마다 다른 폭 줄바꿈·어절 자르기 조건·최소 크기·확장·포기·외곽선 / 맞춤 대상 규칙 2건 / `fit_bubble` 검증 1건 / 짧게 다시 번역 프롬프트 1건), `oxlint` 경고 13개(계산 대상이 바뀔 때만 다시 실행하는 의도적 의존성 생략 1건 추가), 빌드 통과
- 브라우저(직접 그린 테스트 페이지 — 스크린톤 컷 2개, 말풍선 3개(좁고 긴 것·꼬리 달린 것 포함), 스크린톤 위 효과음, 테두리가 끊겨 붙은 말풍선 2개):
  - 6개 중 4개 모양 인식. 스크린톤 위 글자와 테두리가 끊긴 쪽 말풍선은 예상대로 둥근 사각형
  - 번역문을 점점 길게 해서 최소 크기(12px) → 흰 영역 확장 + 주황 점 → "짧게 다시 번역" 버튼 순서로 동작 확인. 가짜 응답으로 요청에 "147자 이내"가 들어가고 번역이 교체되며 주황 점이 사라짐
  - 첫 시도에서 흰 영역 확장이 위아래로 가늘게 튀어나옴 → 중심 기준 균일 확대로 수정. 좁은 끝 줄에 "그"만 남고 단어가 잘림 → 두 글자 미만 줄 금지 + 어절 유지 우선으로 수정
  - 맞춤 토글 끄기/켜기가 `fit_bubble`에 저장되고 표시가 바로 바뀜
  - 이미지 저장 결과가 화면과 같은 모양·줄바꿈으로 그려짐 (6개 영역 34ms)
  - 테스트 캐시·키·세션은 삭제

주의: 테스트는 직접 그린 페이지라 실제 스캔본(가는 손그림 테두리, 톤이 겹친 말풍선, JPEG 노이즈)에서는 인식률이 다를 수 있다. 오판정이 보이면 영역 수정 모드의 말풍선 토글로 해당 항목만 끄면 된다.

## 추가 수정 22 — 말줄임표는 항상 점 2개(..)로

원문의 "……"가 점 개수만큼 번역에 옮겨져(예: `그래..........`) 말풍선 줄바꿈과 글자 크기를 망가뜨리는 경우가 많았다. 번역문의 말줄임표를 **무조건 `..`**로 통일한다.

| 항목 | 내용 |
|---|---|
| 규칙 (`lib/ellipsis.ts`) | 점이 3개 이상 이어지거나 말줄임 문자(`…` = 점 3개, `‥` = 점 2개)가 들어간 자리는 `..`. 일본식 `・・・`, `。。。`, 전각 `．．．`도 포함 |
| 그대로 두는 것 | 마침표 하나, 이미 점 2개인 `..`, 이름 사이 가운뎃점 하나(`앨리스·마가렛`) |
| 적용 위치 | 번역 요청 지침(모델에게 처음부터 `..`로 쓰게 함) + 결과 정리 단계(`sanitizeResults`: 페이지·묶음 번역, 예전 번역 기록, 백업·JSON 불러오기) + 새 영역 번역·문장 재번역·짧게 다시 번역 결과 + 대본에서 직접 고친 번역 |
| 원문 | 원문(`original_text`)은 바꾸지 않음 |

### 검증
- `tsc -b` 통과, `vitest` **187개** 통과(`ellipsis.test.ts` 신규 5건: 점 3개 이상·말줄임 문자와 일본식 점·그대로 둘 것·`sanitizeResults` 적용·번역 지침 포함), `oxlint` 경고 13개(동일), 빌드 통과

## 추가 수정 23 — 메인/서브 엔진 역할 통째로 바꾸기 (버튼 하나로 스위칭)

Gemini를 재인식 보조로 축소한 뒤에도, "나중에 Gemini가 더 나아지면 메인으로 바꾸고 싶다"는 요청에 맞춰 **역할 자체를 뒤집는 기능**을 추가했다. 실측 비교(같은 페이지를 두 엔진에 보내 토큰·품질을 직접 비교)를 해볼 수 있도록 하는 것이 목적.

| 항목 | 내용 |

## 추가 수정 24 — 번역 토큰 소모 줄이기 (프롬프트 캐시·스키마·재요청·빈 페이지)

먼저 실측해 보니 **토큰의 대부분은 이미지가 아니라 텍스트 프롬프트**에서 나가고 있었다. (말풍선 10칸 페이지 기준 이미지 ~765토큰 = 14%, 나머지 86%가 규칙·단어장·맥락) 그래서 이미지가 아니라 프롬프트 구조를 손봤다.

### 1) 프롬프트를 "바뀌는 주기"에 따라 3구간으로 재배치 — 가장 큰 항목
OpenAI·Gemini 모두 **앞에서부터 완전히 동일한 구간**을 캐시해 싸게 계산한다. 그런데 기존 프롬프트는 페이지마다 바뀌는 조각(페이지 경계 안내·화자 힌트)이 **앞쪽**에 있어서 캐시가 200자쯤에서 끊겼다.

| 구간 | 내용 | 바뀌는 주기 |
|---|---|---|
| (A) 고정 | 역할 · 읽기 규칙 · 번역 지침 · 출력 설명 | 절대 안 바뀜 |
| (B) 준고정 | 단어장 → 작품 노트 | 작품 단위 |
| (C) 매번 | 페이지 경계 · 화자 힌트 · 직전 대사 · 내 교정 · 칸 수 · 재요청 안내 | 요청마다 |

이를 위해 `buildContextInstruction`이 한 덩어리 문자열 대신 `{ context(작품 노트), recentContext(직전 대사·교정) }`로 나눠 돌려주도록 바꿨다. (둘을 묶어 두면 페이지마다 노트까지 캐시가 깨짐) `TranslationSettings`에도 `recentContext`가 생겼다.

### 2) 응답 스키마 강제 + 출력 키 축약 (`original_text`/`translated_text` → `jp`/`ko`)
출력 토큰은 입력보다 단가가 몇 배 비싼데, 이 key가 **칸마다 반복**된다(30칸이면 key만 300토큰 이상). 다만 짧은 이름은 모델이 두 필드를 헷갈릴 위험이 있어, **형태를 API가 강제하도록 바꾼 뒤에만** 줄였다.

- OpenAI: `response_format`을 `json_object` → **`json_schema` (strict)** 로 (`lib/responseShape.ts`에 스키마 정의)
- Gemini: `responseSchema`도 같은 형태(`{cells:[{id,jp,ko}]}`)로 통일 — 엔진별로 응답 형태가 갈리던 `output: 'array'|'cells'` 옵션 제거
- 덤: 형태를 스키마가 보장하므로 프롬프트의 "출력 형식 (절대 규칙)" 설명 블록을 크게 줄임
- 뜻이 남는 이름(`jp`/`ko`)을 썼다. `o`/`t`처럼 한 글자로 줄이지 않은 것도 같은 이유

### 3) 재요청(다시 읽기) 프롬프트 슬림화
재요청은 칸 3개짜리 조각마다 **전체 맥락을 그대로 다시** 보내고 있었다. 재요청의 목적은 "안 읽힌 글자를 다시 읽기"이므로 **직전 대사(recentContext)만 뺐다.** 고정 구간·단어장·작품 노트는 그대로 둬야 방금 보낸 첫 요청과 앞부분이 같아져 캐시가 걸리기 때문. 재요청 안내(`RETRY_INSTRUCTION`)도 맥락에 이어 붙이는 대신 `retry: true` 플래그로 **맨 뒤에** 붙게 했다.

### 4) 교정 예시 중복 제거 (8개 → 3개)
사용자 교정이 **작품 노트를 만들 때 재료로도 들어가고, 번역 프롬프트에도 원본 그대로 8개** 또 들어가고 있었다. 노트에 이미 규칙으로 녹아 있으므로 프롬프트에는 가장 최근 3개만 싣는다. (완전히 빼지 않은 이유: 방금 고친 내용이 다음 페이지에 바로 반영되려면 노트 갱신 주기(10장)를 기다릴 수 없음)

### 5) 빈 페이지는 요청 자체를 건너뛰기
말풍선을 못 찾으면 페이지 전체 인식(≈2천 토큰)으로 넘어가는데, 표지 뒷면·여백처럼 글자가 아예 없는 페이지도 매번 요청이 나갔다. YOLO가 이미 계산하던 `darkRatio`(어두운 픽셀 비율)를 `detectSpeechBubbles`가 함께 돌려주도록 하고, **박스 0개 + darkRatio < 0.0015**면 요청 없이 "번역 0건"으로 확정한다. 기준은 보수적으로 잡았다 — 작은 글자 서너 자만 있어도 이 값을 넘으므로 건너뛰지 않는다.

### 6) 격자 JPEG 품질 0.8 → 0.92
비전 토큰은 **이미지의 가로×세로로만 계산되고 파일 용량과 무관**하므로 압축 품질을 올려도 비용은 그대로다. 압축으로 한자 획이 뭉개지면 곧바로 품질 검사 재요청(비싼 경로)으로 이어지므로 넉넉하게 줬다. (절감이 아니라 재요청을 줄이려는 목적)

### 7) 캐시 적중량을 로그로 볼 수 있게
`usageLog`에 `cachedInputTokens`를 추가해 `[tokens] openai · 격자 번역 — 입력 2600 (캐시 2071) / 출력 40`처럼 찍힌다. 위 1번이 실제로 먹히고 있는지 콘솔에서 바로 확인할 수 있다.

### 검증
- `tsc -b` 통과, `vitest` **206개** 통과(프롬프트 캐시 구간 4건·빈 페이지 3건 신규, 맥락 분리·재요청 슬림화·스키마 키 검증 갱신), `oxlint` 경고 13개(동일), 빌드 통과

| | 이전 | 이후 |

- 브라우저(가짜 응답): 첫 요청이 `json_schema`(strict, 키 `id/jp/ko`)로 나가고 응답이 정상 파싱됨. 빈 번역을 받자 재요청이 나가는데 **직전 대사가 빠지고 재요청 안내가 맨 뒤에** 붙은 것 확인. 캐시 토큰이 `[tokens]` 로그에 표시되는 것도 확인

## 추가 수정 26 — 단어장을 작품별로 분리 + OpenAI 5.6 Terra를 기본으로 복구

### 1) 단어장을 작품별로 분리 (A안)
지금까지 단어장은 저장소 키 하나(`manga-glossary-current`)를 **모든 작품이 함께** 썼고, 페이지 번역 프롬프트에는 **통째로·필터 없이** "반드시 이렇게 번역해"라는 강제 규칙으로 들어갔다. 한 작품에서 인물 이름으로 등록한 단어(예: `進 → 신`)가 다른 작품에서 평범한 뜻으로 쓰여도 강제로 바뀌는 구조였다. 반면 작품 노트·내가 고친 번역·단어장 후보는 이미 작품별이었다.

#### 작품을 알아보는 규칙 (`lib/workIdentity.ts`)
| 순서 | 규칙 | 예 |
|---|---|---|
| 1 | 사용자가 **직접 지정한 작품 이름**이 있으면 그것 | 단어장 창 "작품 변경" |
| 2 | 없으면 **ZIP·CBZ 파일 이름에서 권·화 번호를 뗀 제목** | `陽だまりの樹 01` · `陽だまりの樹 第2巻` · `陽だまりの樹 (下)` · `陽だまりの樹_03` → 모두 `陽だまりの樹` |
| 3 | 저장 키는 **전각/반각·대소문자·띄어쓰기·문장부호 차이를 없앤 값** | `One Piece` = `ＯＮＥ　ＰＩＥＣＥ` = `One_Piece` |
| 4 | 제목을 알 수 없는 낱장 이미지(`001.jpg`, `page_012.png`)는 **"이름 없는 작품"** 하나로 모임 | 단어장 창에서 "작품 이름 붙이기" 권장 |

떼어 내는 권·화 표시: `第N巻/話`, `N巻/권/화`, `제N권`, `vol.N`·`v01`·`ch.N`·`#N`, 끝의 숫자(`01`, `01-05`), 괄호 속 권 번호·연도·`Digital`·`上/中/下/前編/後編/完`, 끝의 `上/中/下`. **제목 앞쪽 숫자(`20世紀少年`, `3月のライオン`)와 작가 이름 괄호(`[手塚治虫]`)는 남긴다.**

#### 함께 작품 단위로 묶은 것
단어장만 작품별로 하면 권이 바뀔 때 노트는 끊기고 단어장만 이어지는 어긋남이 생겨서, **작품 노트·내가 고친 번역·단어장 후보도 같은 작품 키**를 쓰게 했다. (예전엔 파일 이름 그대로여서 2권을 열면 1권 노트가 안 보였음)

#### 작품 이름 직접 지정 (단어장 창 상단)
- 파일 이름이 제각각이라 자동으로 안 묶일 때(`hidamari_gaiden.zip` 등) → "작품 변경"에서 **이미 연 작품 목록 중 고르면 그 작품의 단어장·노트를 같이 씀**
- **새 이름을 적으면** 지금까지의 단어장·노트를 그 이름으로 옮김
- ZIP은 "파일 이름 → 작품 이름" 연결을 기억(`manga-work-aliases`), 낱장 이미지는 작품 이름을 그대로 붙여 둠(세션 복원 때도 유지)
- 직접 지정했으면 "파일 이름으로 자동 인식으로 되돌리기" 제공

#### 기존 데이터 옮기기 (여러 번 실행해도 안전)
- 작품 노트·교정·후보: 예전에 **같은 작품의 어느 권으로든** 저장된 것을 모아 옴 (노트는 가장 최근 것, 교정·후보는 합침)
- 단어장: **예전에 작업하던 작품이면** 공통 단어장을 그대로 이어 받고, **처음 여는 작품은 빈 단어장**으로 시작 (다른 작품 단어가 섞이지 않게)
- 공통 단어장은 지우지 않고 남겨서, 단어장 창의 **"예전 공통 단어장 N개"** 에서 항목별 `+` 또는 "모두 가져오기"로 골라 가져올 수 있음. 다 정리했으면 "지우기"
- 단어장을 다 지운 작품에 예전 단어장이 다시 옮겨 오지 않도록, 빈 단어장도 저장

#### 백업 ZIP·드라이브
백업의 단어장·노트·교정은 **복원되는 작품**의 저장소로 합친다. (예전엔 단어장만 "지금 열린 작품"에 합쳐지는 어긋남이 있었음)

### 2) OpenAI 5.6 Terra를 기본으로 복구
6 Luna를 기본으로 쓰니 고어체·붓글씨체 원문(예: 사극 만화의 격식체 나레이션)을 잘못 읽는 경우가 많았다. 같은 페이지를 6 Sol로 읽히면 정확했고, 이전 5.6 Terra도 그 정도는 읽었다.

| 헤더 선택 | 실제 모델 | 역할 |
|---|---|---|
| **5.6 Terra** | `gpt-5.6-terra` | **기본값** |
| 6 Sol | `gpt-6-sol` | 가장 강함 (품질 검사 재요청의 승격 대상) |
| 6 Luna | `gpt-6-luna` | 시험용 — 써 보다가 계속 이상하면 제외 예정 |

- 세대가 섞여서 이름을 이어 붙이지 않고 `OPENAI_MODELS` 표로 매핑
- 저장 키를 `openai-version` → `openai-model`로 옮기며, **예전에 Luna로 저장돼 있던 값은 Terra로 되돌림** (Sol을 골라 뒀던 사람은 그대로 Sol)

### 검증
- `tsc -b` 통과, `vitest` **235개** 통과(작품 판별·이전·이름 변경 26건 신규, 모델 매핑 3건 신규), `oxlint` 경고 13개(동일), 빌드 통과

  - `キングダム 01.zip`은 빈 단어장으로 시작, "예전 공통 단어장 3개"에서 하나만 골라 가져옴
  - 가짜 응답으로 실제 번역 요청 확인: 「キングダム」 요청엔 단어장 1개만, 「陽だまりの樹 第3巻」 요청엔 3개 모두 실림. 모델은 `gpt-5.6-terra`
  - `hidamari_gaiden.zip`을 "작품 변경"에서 「陽だまりの樹」에 연결 → 그 작품 단어장 3개를 그대로 씀
  - 테스트용 데이터는 삭제
